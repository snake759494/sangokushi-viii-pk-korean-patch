# 삼국지 VIII with 파워업키트 (PS2) 한글패치 — 기술 분석

대상: **SLPM-62319**, 일본판 CD, `Sangokushi VIII with Power-Up Kit (Japan).bin/.cue`
(MODE2/2352, 215,923 섹터, 507,850,896 B). 오프셋은 따로 적지 않으면 파일 오프셋,
`VA` 는 실행파일 가상 주소이며 **VA = 파일오프셋 − 0x80 + 0x100000** 이다(9PK 와 같은 규칙).

## 1. 디스크 구성

CD 이미지는 전 섹터가 Mode 2 Form 1 이다. 사용자 데이터 2,048 B 는 섹터 시작에서 +24.
`work/tools/bin2iso.py` 로 2,048 B 평판 ISO(442,210,304 B)를 만들어 분석한다.

| 파일 | LBA | 크기 | 내용 |
| --- | --- | --- | --- |
| `SAN8.BIN` | 24 | 88,096,768 B | 헤더 없는 묶음 파일. 아래 41개 서브파일 |
| `MODULES/*.IRX` | 43,040~ | — | IOP 모듈 |
| `SLPM_623.19` | 43,388 | 5,409,584 B | 실행파일(ELF). 문자열·파일 테이블 포함 |
| `LOGO.PSS` | 100,000 | 3,098,624 B | 동영상 |
| `OPENING.PSS` | 101,513 | 59,164,672 B | 동영상 |
| `ENDING.PSS` | 130,402 | 83,625,984 B | 동영상 |
| `SAN8BGM.ADX` | 171,235 | 91,213,824 B | BGM |
| **빈 영역** | **46,030 ~ 99,999** | **약 110 MB** | 원본에서 사용하지 않음. 커진 파일을 옮길 곳 |

앞까지 53,970 섹터가 비어 있어, 9PK 와 같은 **파일 재배치** 방식을 쓸 수 있다.

## 2. 파일 테이블 (실행파일 안)

`SLPM_623.19` 파일 오프셋 **0x4EB2A0** (VA 0x5EB220) 부터 32바이트 엔트리 45개.

```
[u32 이름포인터][0][u32 시작LBA][0][u32 끝LBA][0][u32 섹터수][0]
```

이름 문자열은 0x509590 부터 (`\F_FONT.S8;1` 등). 9PK 와 같은 구조다.
크기가 바뀌는 파일은 이 표의 시작 LBA·섹터 수를 함께 고쳐야 한다.
`work/tools/extract_originals.py` 가 이 표를 읽어 `work/san8/` 로 서브파일을 뽑는다.

## 3. 글꼴 `F_FONT.S8`

```
0x00000  u32    전각 글리프 수 N = 3,759
0x00004  u16[N] 각 글리프의 Shift-JIS 코드
0x01D64  반각 글리프 256개 : 12x24, 4bpp (144 B/자), 1바이트 코드 순
0x0AD64  전각 글리프 N개   : 24x24, 4bpp (288 B/자), 코드표 순
```

4bpp 는 **하위 니블이 왼쪽 픽셀**, 값 0(투명)~15. 9PK 와 같은 방식이다.
글리프 확인은 `亜`(0x889F, 인덱스 340), `あ`(0x82A0, 인덱스 135) 로 했다.

코드표 3,759자 중 한자 슬롯(0x889F~0xEAA4)은 **3,305자**로 연속이며 인덱스 340 에서
시작한다. 한글 **KS X 1001 완성형 2,350자**를 넣고도 955칸이 남으므로, 9PK 와 똑같이
`亜`(0x889F)부터 차례로 덮어쓰는 방식을 그대로 쓸 수 있다. 사용자 정의 영역(0xF040~)
101자는 코에이 외자이므로 건드리지 않는다.

게임은 전각 글리프를 **2행부터** 화면에 찍는다(위 2행이 윗줄과 겹친다). 한글은 서울한강체 B 22px 로
기준선 21 에 맞춰 2~23행에 그렸다. 처음에 기준선 19 로 그렸을 때는 다음 글자의 0~1행이 글자 아래에
점처럼 비쳐 보였다(스크린샷으로 확인 후 수정). 버튼 아이콘(△○×□ 등)과 드문 한자는 사용자 정의 영역
(0xF040~, 유니코드 사설 영역 U+E0xx 로 표기)에 있어 그대로 쓴다.

## 4. 텍스트 `M_MSG.S8`

9PK 의 `M_MSG.S9` 와 **구조가 다르다.** 8PK 는 `KOEI` 매직이 붙은 2단 컨테이너다.

```
0x000  'KOEI' 00 00 00 00
0x008  u32  바깥 오프셋표의 끝(0xFFFFFFFF 의 위치) = 0x4E8
0x010  u32  0x4D0
0x018  u32[308]  그룹 오프셋표 (데이터 base 0x4F4 기준), 0xFFFFFFFF 로 끝
0x4F4  그룹 데이터

그룹:
  +0x00  u32  머리 크기 hs = 4 + 4*항목수
  +0x04  u32[항목수]  항목 오프셋 (그룹시작 + hs 기준)
  +hs    (앞자리 블록) + 항목 데이터
```

그룹 47 처럼 첫 항목 오프셋이 0 이 아니어서 **항목표와 첫 항목 사이에 3,012 B 의
앞자리 블록**이 있는 경우가 있다(재조립 때 그대로 보존해야 한다).
마지막 그룹 307 은 hs=0 인 꼬리 블록이라 스크립트가 아니다.

**그룹 308개 · 항목 9,378개.** `work/tools/s8text.py` 의 파서·빌더로 다시 묶으면
원본 2,258,944 B 와 **바이트 단위로 완전히 같다**(검증 완료).

### 4.1 항목 스크립트 토큰

| 토큰 | 바이트 | 뜻 |
| --- | --- | --- |
| 텍스트 | Shift-JIS | 화면에 찍히는 글자 |
| `$코드` | `24` + u16 | 제어 코드. 569종 |
| `$코드`+인자 | `24` + u16 + u32 | 인자를 갖는 코드 124종 (예: 0x26, 0x37, 0x554) |
| `@R` | `40 52` | 줄/페이지 구분. 65,274회 |
| NUL | `00` | 문자열 끝 |

자주 쓰이는 코드: `$0x554`(20,342회), `$0x1F`(7,382), `$0x22`(6,505), `$0x21`(5,553),
`$0x38`(4,622), `$0x36`(4,455), `$0x26`(4,121). 인자 유무는
`work/tools/calib_codes.py` 가 통계로 판정해 `work/trans/code_operands.txt` 에 적는다.
이 표로 9,378개 항목을 모두 토큰으로 나눴다 다시 합치면 **원본과 100% 일치**한다.

### 4.2 번역 분량

| 항목 | 값 |
| --- | --- |
| 텍스트 런 | 107,998개 (일본어 포함 98,960개) |
| 일본어 바이트 | 1,297,242 B ≈ 648,600자 |
| 중복 제거 고유 런 | 46,242개 ≈ 430,300자 |

런은 `$` 코드(이름·숫자 변수)로 잘려 있어, 실제 번역 단위는 9PK 의 `units.py` 처럼
한 문장으로 다시 이어 붙여 만들어야 한다.

### 4.3 위치 인자 (점프·페이지 표식)

제어 코드 `$0011`(인자 0), `$0013`(0,1), `$0015`(0~3), `$0019`(0,1), `$053B`(1) 의 인자는
**그룹 안 바이트 위치**다(그룹 첫 항목 시작 기준). 원문의 1,136개가 전부 명령 경계에 떨어진다
(`work/tools/find_offset_codes.py`). 지도 이벤트·오프닝처럼 문장을 이어 찍는 장면이 이 값으로
다음 쪽을 찾는다. 번역으로 길이가 바뀐 채 두면 값이 글자 중간을 가리켜 화면에 「E 없다」
(「이제」의 둘째 바이트 0x45 부터 찍힘), 「R모두의」(`@R` 의 R 부터), 문장 앞 「ト」 같은 잘린 글이 나온다.
`build_text.py` 의 `fix_offsets()` 가 원문·번역의 뼈대(명령·줄바꿈·NUL)를 맞대어 위치를 옮기고,
`work/tools/check_offsets.py` 가 1,136개 모두 원문과 같은 명령을 가리키는지 검사한다.

### 4.4 말투 매크로 (그룹 0)

그룹 0(161항목)이 말투 매크로 표다. 코드 `$05XX` 는 그룹 0 의 항목 `0x05XX − 0x055A` 로 펴지고,
항목 안의 분기 코드(`$0026`·`$0034`·`$0035`·`$0036`…)가 화자(여성·군주 평어·정중·노장·거친 말투)에 따라
어미를 고른다. 한국어도 교착어라 같은 구조를 살렸다. **어미 매크로 앞 어간은 받침으로 끝나게** 쓰고
(`맞았` + `습니다`/`다`), 한국어는 종결어미를 겹칠 수 없으므로 앞 매크로가 이미 문장을 끝내는
순수 종조사 매크로(ね·な·わ·ぞ·よ 등) 11종은 비웠다(`work/tools/macro_ko.py`).

### 4.5 대사 줄 폭

원문은 화면 상자에 맞춰 줄이 나뉘어 있으므로 **그 단위 안 가장 긴 원문 줄**을 폭 한계로 본다
(`work/tools/unit_limits.py` → `work/trans/unit_limits.tsv`). 여러 줄 단위는
`max(단위 원문 최대, min(그룹 90퍼센타일, 28))`, 한 줄 단위는 그룹 90퍼센타일, 어느 쪽이든 그룹 최대를
넘지 않는다. 그룹 최대만 쓰면 한 줄짜리 예외 때문에 한계가 느슨해져 시나리오 개요·연표가 상자 밖으로 나갔다.
M_MSG 문장에는 printf 가 없어 `%` 가 그대로 찍히므로 대사 속 퍼센트는 전각 `％` 로 쓴다.

## 5. 이름 데이터 `D_SCE.S8`

| 표 | 위치 | 레코드 | 내용 |
| --- | --- | --- | --- |
| 주(州) | 0x24 | 17 B × 16 | [이름 5][읽기 7][기타 5] — 幽州~揚州 |
| 도시 | 0x7F0 | 16 B × 50 | [속성 3][번호 1][이름 5][읽기 7] — 遼東~三江 |
| 무장 | 0x2437 | 0x4F B × 658 | 姓 +0x02(5) · 읽기 +0x07(11) · 名 +0x12(5) · 읽기 +0x17(11) · 字 +0x22(5) |
| 그 밖의 이름 표 | 0x24 ~ 무장 표 앞 | 고정 길이 | 아이템·관직·시설 등 549칸 |

그 밖의 이름 표는 레코드 앞에 1바이트 번호가 붙는데, 그 값이 Shift-JIS 선두 바이트 범위(0x81~0x9F)라
「전각 글자에서 시작」 하는 식으로 훑으면 한 칸 밀린 가짜 문자열이 잡힌다.
`work/tools/d_sce_strings.py` 는 **스트라이드와 위상을 먼저 찾아**(같은 간격으로 이름+NUL 이 4번 이상 이어지는 구간)
표를 잡고, 앞 항목 범위와 겹치는 것을 버린다. 가나 읽기 칸(반각)은 모두 비웠다.
글자 수가 늘어도 칸 크기(원래 NUL·공백까지) 안에서만 쓰고 뒤의 채움 바이트는 원본을 유지한다.

## 6. 실행파일 문자열

`work/tools/elf_strings.py` 가 다음 조건으로 뽑는다: 문자열 구간(0x4D0000~0x520000) 안,
앞 4바이트가 포인터 값이 아님, CP932 디코드 가능, 일본어(한자·가나·반각 가나) 비율 기준 이상,
**코드에서 주소가 참조됨**(`elf_refs.py` 의 lui/addiu 추적). `cap` 은 다음 비영 바이트까지의 여유다.
4,257개 중 4,245개를 번역했다. 남은 12개는 공백·데이터 조각과 무명 NPC 이름 조각으로 보이는 가나 한 글자
(`な`·`し`)다. 여러 줄 문자열은 TSV 에 `\n` 으로 적고 줄 수를 원문과 같게 둔다
(`work/tools/fix_elf_multiline.py` 가 첫 줄만 남았던 79개를 다시 넣은 기록).

## 7. 그래픽 `G_*.S8`

두 가지가 섞여 있다.

- **KOEI LZSS 블록**(9PK 와 같은 형식 `[종류][풀린 크기][코드 위치][리터럴 위치]`): G_MAIN · G_STILL · G_EMTMP ·
  G_EHTMP · G_EBTMP1/2 · G_FEINIT · G_WPRESS. `work/tools/s8gfx_all.py` 로 전부 풀린다. 다시 넣을 때는
  `work/tools/s9lz.py`(9PK 에서 만든 압축기, 게임 해제 함수 모형 `title/gamedec.py` 로 되풀어 검증)로 압축해
  원래 블록 자리 안에 넣는다.
- **비압축**: G_SYSTEM · G_GUNGI · G_WARGRP · G_IKBG · G_IKUNIT 등. 앞머리에 1 KB RGBA 팔레트 n개
  (PS2 CLUT 순서: 인덱스 비트 3·4 교환) 뒤 8비트 픽셀. 한 파일 안에 8비트·4비트(바이트당 2픽셀, 낮은 니블 = 왼쪽)
  구간이 섞여 있다. G_IKBG 의 팔레트는 `P_IKKI.S8`.

「획 안쪽 정도」 순서로 늘어놓고 썼는데, 견본의 군단 색 번호가 섞여 글자가 무지개색으로 깨졌다(v1.0.1 에서 수정).
4비트 아이콘은 원본이 명암 단계(글자 1 → 가장자리 3~6 → 바탕 8~11)로 칠해져 있어 니블 값을 밝기 순서로 보고 그린다.
2색 태그(부대 상태)는 테두리·바탕·글자·그림자 네 값만 쓴다.

## 8. CD 섹터

전 섹터가 Mode 2 Form 1 이라, 데이터를 바꾼 섹터마다 EDC(CRC32 변형)와 ECC P/Q(RSPC)를 다시 계산한다
(`work/tools/cdecc.py`). Q 패스는 P 패리티를 포함한 2,236 바이트를 덮는다. 원본 섹터를 다시 계산해
바이트가 같아지는 것으로 구현을 검증했다.

## 9. 남은 과제

- 도시 특징 그림 5종(農耕·商業·技術·城塞·放牧 붓글씨)이 어느 파일에 있는지 찾지 못했다.
- G_GUNGI 의 아주 작은 攻守 타일(높이 5픽셀)은 그대로 두었다.
- 원문이 `{05C2}か` 처럼 종결 매크로 뒤에 의문 조사를 두는 곳(약 1,400곳)은 「~습니다?」 꼴이 되어 어색할 수 있다.
